# 协作协议

所有成员共用本协议。约束的是席位，不是成员：谁坐这个席位就守这一节。详细推理和执行过程留在各自的原生会话，公共文件只写结论、依据要点和位置。被派活的成员只看上下文包里的「成员须知」和自己席位那一节。

## 1. 总则

### 文件与用途

| 文件 | 用途 | 何时读 |
|---|---|---|
| `PROGRESS.md` | 总管的入口：下一步、现状（总管写），待你决定、生效决议、目标表、任务表（生成），加载地图 | 总管每次；成员不读 |
| `protocol.md` | 本协议 | 总管按加载地图读相关一节；成员的那几节由上下文包带上 |
| `log.md` | 每天的决议、任务流转和方向变化 | 收工时写；查历史时搜索 |
| `members.md` | 有哪些成员、型号、能力表、唤醒和续接方式（由班子配置生成） | 选人、派活时 |
| `internal/` | 工具自己用的数据，都不手改：`flow/`（目标、任务、议题的事件，每个编号一份 `.jsonl`，唯一事实来源，只经 `core/flow.py` 写）、`plans/`（`roster.json` 和项目自己覆盖的骨架）、`runs/`（派活脚本写的每次派活记录，含会话号，供看板读取） | 不用读，用 `flow.py 上下文` / `可走`；查某次派活的结果时看 `runs/` |
| `outputs/` | 管理性产出：验收结论、确认依据，以及项目外证据的快照，按编号分目录；业务交付不放这里（见「工作区」） | 确认时 |
| `decisions.md` | 生效决议全文 | 任务卡引用或要改方向时 |
| `issues/I00x-*.md` | 朝会：需要多个成员分别发表观点的讨论 | 开朝会、写总结或裁决时 |
| `goals/G00x.md` | 目标卡：要什么、总裁批准的流程（只放定稿内容） | 新目标、改流程，或做属于它的任务时 |
| `goals/G00x/questions.md`、`proposal.md`、其他 Markdown | 目标自己的文档：`questions.md` 放还没想清楚的问题，`proposal.md` 放定下来的全部内容（含硬约束），调研等材料也放这里；按需创建，随目标卡归档 | 聊想法、聊方案时；成员的上下文包只给 `proposal.md` 的路径，不带问题 |
| `tasks/G00x-Tn-*.md` | 任务卡：流转、交接 | 被点名时 |
| `lessons.md` | 可复用的做法和坑 | 总管开始同类工作前；要成员知道的，写进交接 |
| `archive/` | 已关闭的议题、目标和任务，被取代的决议 | 查历史时，先搜索 |

### 工作区
<!-- role: lead -->
`collab/` 是管理账本，只记谁在什么时候凭什么做了什么、结果在哪；做出来的东西放在和它并列的 `work/` 里。判断规则：写给总管和总裁做决定的留在 `collab/`（议题、发言、决议、日志、流转、运行记录、卡片、经验），项目本身要用的放进 `work/` 或项目原有的位置。

```
work/
  G001/                        工作目录：一个目标一个，名字是目标编号，目标批准时自动建（起草阶段不建空目录）
    G001-T1/                   交付
    .scratch/<成员>/G001-T1/   工位
```

- **交付**：默认放 `<工作目录>/<任务编号>/`；代码项目直接改项目原有的文件（`src/` 等），不另复制。`--证据` 写相对项目根的路径。
- **工位**：`<工作目录>/.scratch/<成员>/<任务编号>/`，放本次任务的草稿和中间笔记，只写自己的。工位不是证据，验收只看交付；目标归档时可以清掉，默认不进 git。
- **从结果出发**：接手别人做过的任务、做后续阶段时，只从交付和 `collab/` 的记录出发，不读别人的工位。

### 基本规则
<!-- role: lead -->

1. 只读加载地图要求的文件；需要历史时先搜索，再读命中部分。
2. 修改任何公共文件前重新读取它，只改属于自己的分区，不改写他人内容。
3. 讨论中的意见不是决议。只有总裁确认后写入 `decisions.md` 的才是。
4. 不确定的结果写「未知」或「未验证」，不能推断为完成。
5. 不在公共文件中粘贴大段过程、日志或代码，写位置即可。
6. 忠于目标：区分硬约束和可替换的做法；有更合适的方案就说明依据与取舍；可以反对、报告失败和不确定，不为顺从而隐藏问题。
7. 路径：协作文件直接写文件名（都在 `collab/` 下）；其他项目文件，链接写 `../路径`，反引号里写相对项目根的路径。

### 成员须知
<!-- role: executor, reviewer, acceptance -->
- 只按上下文包工作：不读 PROGRESS 和整份协议，不改卡片里的生成块；流转只用「你能走的边」里的命令写。
- 守住交接里的硬约束，可替换的做法可以换；改公共文件前先重读，只改自己的部分。
- 如实：没验证的写「未验证」，不推断为完成；有更好的做法说明依据，可以反对、报告失败和不确定。
- 交付放「现状」给的位置（代码直接改项目原有文件），`--证据` 写相对项目根的路径；草稿放自己的工位，工位不算证据。
- 接手前人的工作只看交付和流转记录，不读别人的工位；公共文件不贴大段过程，写位置。

## 2. 席位

席位随任务或目标流程指定，同一成员在不同任务里可以坐不同席位。成员能做什么（权限、型号）看 `members.md`；行为边界看任务卡的「硬约束」「授权」。

### 总裁
- 定方向，批准总管的分析和整体框架，确认决议，裁决议题，授权超出已批准框架的事；说"定了"的事才进 `decisions.md`。
- 不写任何文件：在对话或看板上做的决定由总管代记（见「总管」第 7 条）。

### 总管
<!-- role: lead -->
1. **先搭框架，看图批准**：和总裁聊清楚后，总裁说「搭框架」，总管拆任务、建任务卡、定依赖和人选，交给总裁在看板上看图、提意见、改图。**总裁批准前，一律不开工，总管自己做也一样。** 凡是要改文件或产生交付的事，都要先有目标、任务卡和批准，不看事情大小；只有提问和讨论不用。
2. **框架内自主**：框架批准后，执行中的问题由总管自己解决：调整步骤、换人、返工、补任务都可以，补的任务也要建卡，不用再单独批准，图上会标出和批准版的差别。只有「上报」一节所列的绝对阻塞才上报总裁。
3. **用人不疑，验收在目标层面**：默认相信成员自己完成的任务，不逐个任务交叉验证；默认由总管按成功标准做目标验收，要第三方就在框架里写验收阶段（见「流程 · 验收」）。
4. **汇报**：先写现状和要总裁决定的事；过程和证据放在卡里，写位置。
5. **待你决定**：PROGRESS「待你决定」由 `flow.py` 生成，列出所有持有人是总裁的目标和任务（待批准的框架、待确认的目标、受阻到总裁的任务）。要总裁拍板时，总管把任务上报或转交给总裁并写 `--方案`「A …；B …」和 `--建议`，目标走「提交」「目标验收」；总裁拍板后由总管代记，这一条自动消失，日志记一行。
6. **批准批注**：总裁在看板批准时写的批注，会以「总裁意见（总管处理）」出现在「待你决定」。开工前先读，照办后用 `flow.py 记 G00x 进展 --说明 "怎么处理的"` 记一条，它才消失。
7. **代记总裁**：总裁不写任何文件。总裁在对话里做的、影响流转的决定（批准、退回、解除、选方案、叫停），都由总管用 `flow.py 记 … --作为 总裁 --依据 "原话要点"` 记下。

### 执行
<!-- role: executor -->
- 结束前必须写一条：做完写 `交付`（`--说明` 写做了什么、自测结果，可复核的原始输出写成文件），卡住写 `上报`（写原因和可选方案，默认给总管，不直接找总裁）。不给结论就停止的，派活脚本代写「上报：未声明结果」。

### 验收
<!-- role: reviewer, acceptance -->
1. 以目标为准：成功标准达到就判「通过」，不因还能更好而不通过；只提真正影响结果的问题，改进建议可写进结论，但不作通过条件，要返工由总管决定。
2. 像使用者一样试用交付物：能跑的跑，能打开的打开，不只核对文字。
3. 用 `确认 --结果 通过|需补充|未通过` 写结论，`--说明` 写核查了什么、证据位置、未覆盖项；需补充默认退回上次交付人。
4. 确认人不能是上次交付人。第三方验收者不能是执行者本人，开新会话，只依据目标卡、交付物和流转判断，意见由本人写，总管不改写。

### 与会者（朝会）
<!-- role: attendee -->
- 只看派活脚本给的上下文包：问题、你的视角、所挂目标、你上次之后的新发言。第一次发言独立给判断：能看到叫你的那句话之前的公开发言，看不到和你同一句话叫来的人的回答。
- 直接用 Markdown 写发言作为最后回复，系统记到黑板上；不用跑命令，不改任何文件。
- 只有总裁能叫人：你写的 `@名字` 只是普通文字，想听谁的意见就写给总裁。两个记号：只给总裁和总管看的写 `<私下 总裁>…</私下>`；没有要补充的只回 `[PASS]`。
- 黑板放结论和要点；长材料写到 `collab/issues/I00x/<你>/`，发言里贴链接。

## 3. 流程

### 目标与流程
<!-- role: lead -->
流转只用 `core/flow.py` 写（下称 flow）；卡片和 PROGRESS 里的生成块由它重写，不手改。

#### 起草
- **每个想法先建目标卡**，哪怕不做：`flow 建立 目标 --标题 … --依据 "总裁原话"`（默认通用，要调研或开发模板加 `--类型 调研|开发`），状态「起草」。总管填「要什么」（白话，三句话以内，说清做什么、做完得到什么）和「成功标准」，两项必填；硬约束、可替换的做法写进方案。想法、讨论、方案都放在这张卡下，不放项目的 `docs/` 之类别处；项目自身的文档（用户手册、设计文档等）不受影响。
- **三个阶段**：想法 → 讨论 → 方案，都是「起草」状态，卡头「阶段」区分，默认「想法」；换阶段 `flow 记 G00x 起草阶段 --结果 想法|讨论|方案`（只在起草状态下可写）。小事可从想法直接搭框架。批准只有框架这一次，方案不单独批准。
- **文档**按需创建：`goals/G00x/questions.md` 只放「## 待解决」「## 已解决」，解决后结论写进方案，这里留一行去向（由总管代记）；`goals/G00x/proposal.md` 放定下来的全部内容，总裁平时只看它。起草中的目标在 PROGRESS 只汇总一行，看板「想法」页按阶段分组。
- 暂时不做的 `flow 记 G00x 暂停 --说明 …`（起草中也能暂停，恢复后回到原来的阶段），不要的 `取消`。

#### 搭框架与改图
- 写一份框架 JSON，运行 `flow 框架 G00x --文件 框架.json`，一次写好阶段和全部任务卡（状态「规划中」），文件可放在 `collab/internal/plans/`。例：`{"阶段": [{"序": 1, "名称": "开发", "类型": "执行", "前置": [], "任务": [{"键": "mod", "标题": "…", "执行": "成员", "确认": "总管", "前置": [], "目的": "…", "硬约束": "…", "交付物": "…", "验收标准": "…"}]}]}`。
- 每个阶段至少一张卡；目的、交付物、验收标准必填；想不清的任务先建粗略的卡，在目的里写明什么时候细化。依赖默认由阶段前置推出，更细的在任务上写 `前置`（排在前面的任务的键）。
- **改图**：改文件后重跑同一条命令，自动记下这轮改了什么，框架版本加一；待批准时可以直接改，不用先退回。批准前改图是整版重写，批准后按「键」认任务、新卡续号、去掉的任务被取消（已开工的不能去掉）。编号和字段的细则见 `core/README.md`「改图」。

#### 批准与执行
- **提交和批准**：`flow 记 G00x 提交 --说明 … --建议 …` 交总裁看图，任务卡不全会被拒绝。总裁在看板批准，或在对话里说、总管代记 `flow 记 G00x 批准 --作为 总裁 --依据 "原话"`。批准时任务一起转为「已批准」，并存一份批准版，之后图上显示实际和它的差别。总裁的意见出现在「待你决定」，改框架后消失。
- **所有任务必须归属目标**。一件小事就是一个目标加一张卡，可以由总管自己执行，也要批准。批准后补任务同样用 `flow 框架`（或 `flow 建立 任务 --目标 G00x --阶段 n --标题 … --依据 …` 后填好交接）。
- **总管自己执行**：`flow 开工 G00x-Tn`，一条命令写派发和接手。
- 阶段进度由子任务推出：阶段的任务全部结束且至少一个通过才算通过；前置阶段没通过不能派。前面阶段的任务被重开，后面阶段的通过自动失效。不手写阶段状态。
- 所有阶段通过后，总管 `flow 记 G00x 目标验收 --说明 … --方案 … --建议 …`，总裁确认后代记「完成」，或「打回」。「汇报」不是阶段。
- 框架内的调整（增删阶段、换人、补任务）由总管决定，`flow 记 G00x 变更 --变更项 … --说明 …`；改目标、成功标准、方案里的硬约束或验收结构要带 `--依据` 总裁原话。
- 顺序、人选、依赖由 flow 在写入时检查，确需偏离加 `--越过 "理由"`（见「校验与闸门」）。**任务规划中、目标没批准时不能开工，这一条不能越过。**

### 多个目标
<!-- role: lead -->
- 同时「进行中」的目标不超过 3 个；再多的留在「待批准」或改「暂停」。成员是共用的，同时开太多每个都慢。
- 目标有先后时，在卡头下加一行 `优先：1 ｜ 依赖：G00x ｜ 截止：…`；「优先」1 最高，由总裁定，资源冲突时（如两个目标都要同一成员）总管按优先顺序排；前置目标没完成前，这个目标不派发。
- 每张任务卡只属于一个目标，编号里带目标号（见「记录规范 · 编号」）；「待你决定」每条写目标或任务号，看板按目标归类。
- 目标验收后（第三方验收的结论用原文），总裁确认、总管代记「完成」，用 `flow 归档 G00x` 把目标卡和 `goals/G00x/` 一起移到 `archive/goals/`；流转事件留在 `internal/flow/`，不搬。

### 派活
<!-- role: lead -->
- **前提**：所属目标已批准，任务卡的交接已写好（flow 检查）。
- **派活脚本**：`dispatch start <编号> 执行|确认 <成员> "<启动语>"`。脚本代写派发、接手（确认席位时代写转交），把 `flow 上下文` 的上下文包拼进启动语，结束后写一条进展；成员没写结束边就代写上报给总管。启动语只写这次要做什么，不用再写「读哪些文件」。
- **选人**：流程表或任务卡已写人选的照办。没写的由总管按 `members.md`「能力表」选：先定难度，简单的（整理、格式、批量、查资料）用能胜任的最便宜的成员，中等用 B 档，难或关键的用 A 档；返工多了按「状态流转」升档。
- **身份**：成员都是通用型，身份由总管按任务写在卡上（任务卡「身份」、议题「与会」的视角）。
- **会话**：`dispatch start` 每次开新会话；返工、追问用 `dispatch continue <编号> 执行|确认 "…"`，续接这个任务这个席位最近的会话（上下文已经太长、成员权限改过时改用 `start` 开新的）。第三方验收总是开新会话。朝会续接该成员在本目标里最近一个正常结束的会话（项目级议题按议题），第 1 轮的独立由派活脚本只喂问题来保证。
- **权限**：由班子配置决定，写在 `members.md`；任务卡只写行为边界。

### 状态流转
<!-- role: lead -->
- 任务状态：已批准 → 已交接 → 执行中 → 待验收 → 通过；另有受阻、暂停、未通过、取消。持有人（现在谁手里拿着）由事件回放推出，任何时刻恰好一个。
- 只用 `flow 记 <编号> <边>` 写，一条事件一条边：建立、派发、接手、交付、确认（通过 / 需补充 / 未通过）、转交、上报、解除、改派、暂停、恢复、重开、取消（批准前改框架用的撤下、重拟由 `flow 框架` 自动写，不手记）；另有变更（改了交接哪几项）、进展、更正（作废某个 seq）。不合法的写法当场被拒，并列出现在能走的边；`flow 可走 <编号>` 随时可查。
- 谁写：执行者写交付、上报；确认人写确认；派活脚本写派发、接手、进展；其余由总管写，总裁的决定由总管代记。
- 同一执行人连续第 2 次需补充时提示升档（升一档续做，流转里写明原因）；第 3 次只能改派、转交或上报。总裁判的需补充不计。
- 卡头、任务卡「流转」、目标卡「流程」「变更」、PROGRESS 的生成块都由 flow 重写；手改会被检查报出，用 `flow 渲染` 恢复。

### 验收
<!-- role: lead, acceptance -->
验收在目标层面做，不逐个任务做；只要总目标和成功标准达到就算通过，返工和改进由总管决定是否采纳。

| 层面 | 默认 | 例外 |
|---|---|---|
| 任务 | 用人不疑：执行者交付并自测，总管「确认」通过 | 无 |
| 阶段 | 无 | 框架里写了验收阶段的，派其他成员开新会话验 |
| 目标 | 总管按成功标准写「目标验收」，总裁确认「完成」 | 对外交付、不可逆或方向性的结果由总裁拍板 |

### 上报
<!-- role: lead -->
框架批准后，总管在框架内自主解决问题，只有以下绝对阻塞才把任务上报或转交给总裁（`--给 总裁 --方案 … --建议 …`），它会自动出现在「待你决定」：
- 要改目标、成功标准、硬约束或验收结构
- 需要只有总裁能给的东西：授权、账号或登录、付费、不可逆操作的许可
- 与生效决议冲突，或证据推翻了决议的前提
- 总管穷尽办法仍无法推进

### 收工清单
<!-- role: lead -->
1. `log.md` 写今天的决议、任务流转和方向变化。
2. 更新 PROGRESS「现状」「▶ 下一步」（只有这两段由总管写）。
3. 通过的任务卡移到 `archive/tasks/`；完成或取消的目标用 `flow 归档 G00x`，漏移目录 `flow 检查` 会报错。
4. 已裁决的议题：结论写入决议，文件移到 `archive/issues/`。
5. 不再约束当前工作的决议，整段移到 `archive/decisions.md`（`decisions.md` 里留下的都是生效的，PROGRESS「生效决议」由它生成）。

### 校验与闸门
<!-- role: lead -->
以下由工具强制，不靠自觉：
- **写入时**：flow 拒绝不合法的事件。硬错误（边不存在、必填缺失、成员不存在、证据不存在）不能越过；规则错误（状态不允许、发起方不对、人选或阶段顺序不符、返工超上限等）只有总管、总裁能 `--越过 "理由"`，看板标为偏离。
- **检查**：`core/check.py`（新结构项目调用 `flow 检查`）报出回放不一致、持有人缺失、未结束任务的证据不存在、生成块被改、阶段缺人选、未登记的模板差异、叙述过时等。看板项目页顶部显示结果。
- **每轮结束**：项目的 `.claude/settings.json` 装有 Stop hook（`init.sh` 新建项目时自动装，已有项目运行 `init.sh hook`）。检查有错时，Claude 这一轮不能结束，先改好。git 项目有未提交的改动却没有总管执行中的任务时，只提醒不阻止。
- **改文件前**：同一份配置里的 PreToolUse hook：项目里没有总管「执行中」的任务时，总管的 `Edit`、`Write` 改项目文件会被拒绝，`collab/` 账本不拦，派活脚本启动的成员不拦。Bash 直接写文件拦不住。
- **派活前**：派活脚本先跑检查（误报才用 `--skip-check "理由"`），再经 flow 写派发和接手；不合法就不派，确需偏离用 `--override "理由"`，记入事件和运行记录。

## 4. 朝会
<!-- role: lead -->

朝会都由总裁发起，像群聊一样在看板的朝会页（`/p/<项目>/meet/I00x`）进行。议题属于项目，可挂到目标上；框架会审一定挂在待批准的目标上。

1. 搭会议室：总裁说要开会，总管一条命令搭好：`dispatch room --标题 … --与会 成员:视角 … --依据 "总裁原话" --问题 … --开场 …`。它建议题、写「问题」和「开场约定」（这场会要什么、已知情况、资料位置；软约定，成员可以看、不是必须看，不限制读写），对每位与会者做一次真实的最小调用确认能启动、已登录，全部就绪就直接进「讨论中」并给出会议室地址；有人没就绪则停在起草，处理后 `dispatch ready I00x` 重查。框架会审加 `--类型 会审 --目标 G00x`。与会者尽量来自不同应用或型号。
2. 讨论：总裁进入会议室直接 @ 谁就叫醒谁，不用再点「开始讨论」；成员不抢先发言。只有总裁的 @ 能叫醒人，成员写的 @ 是普通文字。中途可在页面「＋加人」把名单外的可用成员拉进来，他第一次发言能看到叫醒他的那句话之前的全部公开发言（看不到私下发言；同一句话叫醒的人互相独立）。叫人失败页面显示原因，可「补叫」，补叫会带上错过的发言。运行中可停止或让它用已有内容收尾，每次运行有步数和时间上限，到上限自动收尾。发言由派活脚本写进 `internal/flow/I00x.jsonl`，卡里的发言区是生成的索引，不手改。命令行等价：`dispatch meet I00x --wake 成员 …`。
3. 收尾：总裁讨论完点「结束讨论」或说「收口 I00x」。总管用 `flow 上下文 I00x --给 总管` 读全部发言（含私下），在卡里写「总结」——共识、分歧（各方立场、依据、代价）、建议，再记 `flow 记 I00x 总结 --说明 … --方案 … --建议 …`，议题进「待你决定」。
4. 裁决：总裁在朝会页写裁决（原话记作依据），或总管带原话代记 `flow 记 I00x 裁决 --作为 总裁 --依据 … --说明 …`；结论写入决议，需要的后续开目标或任务。框架会审不单独裁决：总裁批准或退回目标时一起结束。还想再议用「继续讨论」。
5. 归档：已裁决的议题卡随目标移到 `archive/issues/`，项目级的单独归档；事件文件不搬。

议题状态：起草（总管）→ 讨论中（总裁主持）→ 收口中（总管）→ 待裁决（总裁）→ 已裁决；未结束的可取消。私下发言成员的上下文包里不出现，但成员有读文件权限，只是软保密。

## 5. 记录规范

### 写入规则
<!-- role: lead -->

| 位置 | 谁写 | 方式 | 上限 |
|---|---|---|---|
| PROGRESS「现状」 | 总管 | 覆盖 | ≤5 行，每行 ≤80 字 |
| PROGRESS「▶ 下一步」 | 总管 | 覆盖 | 1 条 |
| PROGRESS「待你决定」「生效决议」「目标」「任务」 | flow 生成 | 不手改 | PROGRESS 整份 ≤3KB |
| `internal/flow/*.jsonl` | 只经 flow | 只追加 | — |
| `log.md` | 总管（收工时） | 新的在上，一行一条 | 每天 ≤5 条，每条 ≤60 字 |
| 议题「问题」「总结」 | 总管 | 问题开会前写好、开会后不改；总结收口时写一次 | — |
| 议题卡头、「与会」「发言」「裁决」 | flow 生成 | 不手改；与会和视角在「建立」「变更」事件里，发言由派活脚本和朝会页写事件 | 发言不限长，黑板放要点，长材料贴链接 |
| `decisions.md` | 总裁说"定了"之后 | 新增条目，不改旧条目 | — |
| 目标卡「要什么」 | 总管起草，总裁批准 | 改目标、成功标准要总裁批准，并记「变更」事件 | 要什么三句话以内 |
| `goals/G00x/questions.md` | 总管代记 | 只放待解决、已解决；解决后结论写进方案，这里留一行去向 | — |
| `goals/G00x/proposal.md` | 总管起草 | 覆盖，保持当前版本；批准后改硬约束要总裁同意，并记「变更」事件 | — |
| 目标卡卡头、「流程」「变更」 | flow 生成 | 不手改；阶段和人选在「提交」「批准」「变更」事件里 | — |
| 任务卡「交接」 | 派发人 | 交接时填好；改动记「变更」事件 | 超过 10 行的规格写进项目文档再链接 |
| 任务卡卡头、「流转」 | flow 生成 | 不手改；用 `flow 记` 写事件 | 说明 ≤60 字，证据写路径 |
| 任务卡「备注」 | 执行者或验收者 | 追加，标明日期和经办人 | 长内容写成文件放链接 |
| `members.md` | 班子配置生成（`init.sh team-sync`） | 只手写「本项目补充」一节 | — |
| `lessons.md` | 总管（成员的经验写在交付说明里，由总管整理进来） | 一条一行 | ≤20 条，超出就合并 |

### 编号
<!-- role: lead -->
- 议题 `I001`、目标 `G001`、决议 `D001`，各自递增，不复用。
- 任务按目标编号：`G003-T1`、`G003-T2`……，目标内从 1 递增；编号里已有目标，卡头不再写「目标」，只写「阶段」。不能新建没有目标的任务；旧项目已有的 `T00x` 保留，不改。
- 任务换目标时不改编号：原卡流转写「转到 G00x」并结束，在新目标下另开一张卡。
- 目标、任务和议题的编号由 `flow 建立` 在锁内分配并生成卡片，不手工取号、不复制模板。

### 原生会话记录
派活脚本启动的会话，会话号由运行记录自动记下，不用手写。总管手记的流转说明和决议来源要引用某次原生会话时，末尾写 `应用「会话名」日期`，例如 `Codex「G003-T1 接口实验」10-18`；没有会话名时写能找到它的信息。

### 决议变更
决议不改原文。新决议注明「取代：D00x」，PROGRESS 中替换对应行，旧条目整段移到 `archive/decisions.md`。
